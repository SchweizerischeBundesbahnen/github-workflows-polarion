# CLAUDE.md

## Project Purpose

This repository contains **GitHub Actions workflows (reusable and caller/CI)** and the Polarion Semgrep rule pack that one of them runs. There is no application code and no build system.

## Repository Structure

- `.github/workflows/reusable-*.yml` — Reusable workflows called by other repositories via `workflow_call`
- `.github/workflows/*.yml` (non-reusable) — Caller workflows that this repo uses itself, plus CI workflows (actionlint, PR checks, labeler, stale)

## Conventions

- All GitHub Actions must be pinned to full commit SHAs with a version comment (e.g. `uses: actions/checkout@<sha> # v6.0.2`)
- Workflows must set `permissions: {}` at the top level and grant only required permissions at the job level
- Checkout steps must include `persist-credentials: false` — exceptions:
  - `reusable-claude-code-review.yml` — `claude-code-action` needs git credentials for PR branch fetch
  - `reusable-claude.yml` — `claude-code-action` needs git credentials to operate on the PR branch
  - `reusable-actionlint.yml` — reviewdog falls back to `git fetch` for diff fetching on private repos
- Reusable workflows accept secrets via `workflow_call` — never hardcode secrets or tokens
- Use `${{ github.repository_owner }}` instead of hardcoding the org name to keep workflows portable — except where a reusable workflow checks out its OWN source, which uses `${{ job.workflow_repository }}` and `${{ job.workflow_sha }}` so the caller's `uses:` ref decides that content too. Those four `job.workflow_*` properties do not exist on GitHub Enterprise Server. They were unmodelled by upstream actionlint (rhysd/actionlint#647) and needed a `.github/actionlint.yaml` filter; the maintained fork models them, so that file is gone — do not reintroduce it for this
- **actionlint is `kjanat/actionlint`, not `rhysd/actionlint`.** Upstream stopped at v1.7.12 with its last commit on 2026-04-19 and the author unreachable (rhysd/actionlint#719); the fork is the maintained successor, and `reviewdog/action-actionlint` has run it since v1.75.0. The action bakes its binary in and exposes no input to choose the version, so the `rev` in `.pre-commit-config.yaml` has to be reconciled with what the action bundles by reading its release notes — the action's own tag does not name it. When the two drift, the commit gate and CI disagree about whether a workflow is valid, and the CI-only failure reads as a defect in whatever pull request happens to be open: measured on `5535848`, which moved the action alone and turned `main` red. The two sides are read by different Renovate managers, so a `renovate.json` rule groups them into one branch and sets `automerge: false` on it — both parts are load-bearing, because the shared preset automerges `github-actions` and `pre-commit` by branch with no pull request at all, so a grouped bump would otherwise land unread and the reconciliation this bullet describes could never happen. The fork also supplies `cache-mode` and `uses: $/...` support, neither of which upstream can parse
- **`cache-mode` is the CALLER's cap, so nothing published here can satisfy it for a consumer.** It limits what a called workflow may request, and actionlint's `cache-call-unrestricted` fires on the call site, so a reusable workflow cannot set it on behalf of the repositories that call it — the line has to exist in each consumer's own caller, under every low-trust trigger (`issues`, `issue_comment`, `pull_request_review`, `pull_request_review_comment`). A finding of this shape therefore fans out rather than landing once: the actionlint fork upgrade turned roughly 38 consumer repositories red on their own `add-issue-to-project.yml`, while `539602e` could only fix this repository's two callers. The templates those repositories are generated from are where the fix stops recurring
- Commit messages follow [Conventional Commits](https://www.conventionalcommits.org/)
- CodeQL advanced setup and CodeQL default setup are mutually exclusive on a repository, and the loser fails late: with default setup enabled, an advanced analysis runs to completion and is rejected only at upload, with `CodeQL analyses from advanced configurations cannot be processed when the default setup is enabled` (measured 2026-09-21 on this repository, which uses default setup for `actions`). The reverse is silent and worse: enabling advanced setup turns default setup off, and every language the advanced workflow does not name stops being scanned with no signal beyond a configuration on the Code Scanning page whose last scan never advances. `gh api repos/<O>/<R>/code-scanning/default-setup` answers which mode a repository is in before either workflow is added to it
- `polarion-semgrep-rules/tests/fixtures/` holds deliberately vulnerable Java and configuration files, and a workflow that scans a consumer repository must exclude the rule pack checkout path. Semgrep's built-in `.semgrepignore` already skips `tests/`, so the exclusion looks redundant and is not: a consumer repository that ships its own `.semgrepignore` REPLACES the built-in list rather than adding to it, and the fixtures then land on that repository — measured 2026-08-19 at 42 findings against a consumer whose `.semgrepignore` contained only `node_modules/`, versus 0 with `--exclude`. The same built-in list is why the rule baseline covers `src/main` only: `src/test/java` matches `test/` and is never scanned
- Verify a rule-pack change with `SEMGREP="uvx semgrep==$(cat polarion-semgrep-rules/SEMGREP_VERSION)" bash polarion-semgrep-rules/tests/test_rules.sh` — without the `SEMGREP` override the suite runs whatever semgrep is on PATH, which is not the version the rule baseline was measured on
- Re-measure the corpus with `POLARION_TARGETS_DIR=<dir> bash polarion-semgrep-rules/tests/measure_corpus.sh` rather than by hand — it pins the semgrep version and the excludes that decide whether two measurements are comparable, prints the per-rule breakdown so a total that held while its composition changed is visible, and fails on a missing target instead of skipping it
- Probe a rule against arbitrary code with `bash polarion-semgrep-rules/tests/probe_rule.sh <rule|rules-dir> <target>…` rather than calling semgrep by hand — it pins the version, prints the per-file count with line numbers, and closes both doors into a reassuring 0. It refuses to print a count at all when semgrep exited non-zero, which is the exit-7 case below reaching you as a failure; and it prints the scanned-file count beside the finding count and exits 1 when that is zero, because a target semgrep never read — an extension that does not map to the rule's language, or a path the built-in `.semgrepignore` skips, which is why probing `tests/fixtures/` directly reports nothing — otherwise reports 0 findings and exit 0, indistinguishable from a rule that ran and matched nothing
- CodeQL's `actions/untrusted-checkout` fires on the NAME of the checkout's `ref` expression as well as on where the value comes from: under a `workflow_call` trigger a field name matching `.*(head|branch|ref).*` or `.*(head|sha|commit).*` is flagged on its own, whatever it holds. That test binds only to the contexts the extractor models — `inputs`, `env`, `steps`, `needs`, `matrix`, `jobs.<id>.outputs` — with `github.*` excluded from it and reached through dataflow instead, and the `job` context modelled nowhere, which is why `ref: ${{ job.workflow_sha }}` is NOT flagged although `workflow_sha` matches the second regex (`UntrustedCheckoutQuery.qll` and `Ast.qll`, read 2026-08-22; 0 alerts on the PR #100 merge ref). So renaming an input clears such an alert while the caller still chooses the checkout — take the caller's control away instead
- A workflow change cannot be exercised from its own branch through `workflow_dispatch`: the dispatch API answers `404 … not found on the default branch` for a file that exists only on the branch. Verify one with a temporary caller triggered `on: push` limited to that branch, then delete it in the same pull request
- A literal single quote inside a single-quoted YAML scalar must be DOUBLED — `'[^"''\n]*'`, never `'[^"'\n]*'`. Written singly the file is invalid YAML, semgrep loads no rule at all from the `--config` directory, and every target reports 0 findings. The only tell is the **exit code 7**: under `--quiet` both streams are empty and nothing is printed, without `--quiet` stderr carries `[ERROR] invalid configuration file found`, and under `--json` those errors sit in `.errors[]` at `level: error` while stderr stays empty — so a `2>/dev/null` redirect hides no diagnostic and checking semgrep's exit status is what catches this. Measured 2026-08-20 on semgrep 1.172.0 over the pack's own fixtures: 42 findings clean, 0 with one quote undoubled, 0 with a rule's `id:` key renamed, exit 7 in the plain, `--quiet` and `--json` forms alike
- Express a rule's suppression clause as a `pattern-not-inside` over the enclosing scope, never as a `pattern-not-regex`: the regex is applied to the matched REGION AS TEXT, so a comment naming the hardening silences the rule, and widening the pattern to reach another shape moves the region out from under the regex. Both failures are silent. Measured 2026-08-22 on semgrep 1.172.0: `// TODO: switch to SecureUberspector` cleared an ERROR finding, and a genuinely vulnerable case in the pack's own fixture had been recorded as a shape the pattern could not reach when the pattern reached it perfectly well and its own comment was suppressing it. In such a clause `$QUALIFIER.CONSTANT` matches the qualified, fully qualified and static-imported spellings alike, whereas the deep-expression form `<... CONSTANT ...>` matches none of the three — and a bare `$RET $METHOD(...)` wrapper matches neither a constructor nor a static initializer, so a construction outside any method needs a `class $CLASS { ... }` wrapper — which does match an `enum` — and therefore class-scoped suppression. Where the clause must hold for a SPECIFIC receiver, bind it to the metavariable the positive pattern already binds: semgrep unifies it into `pattern-not-inside` and `pattern-not`, whereas a free metavariable lets hardening applied to any object in the method clear every finding in it. Ordering needs more than that — a `pattern-not-inside` over the method matches wherever the call sits, so hardening placed AFTER the object was created still suppresses; carry the creation call inside a `pattern-not` sequence instead, which also means one clause per creation call rather than a shared `pattern-either`

## Workflow Naming

- Reusable workflows: `reusable-<name>.yml` with trigger `workflow_call`
- Caller workflows: `<name>.yml` that reference the reusable version via `uses:`

## Review Architecture

- Claude Code Review (`reusable-claude-code-review.yml`) runs on `pull_request` events — reviews code and triages previous review threads (from Claude, bot reviewers, and human reviewers)
- Claude Code (`reusable-claude.yml`) runs on `issue_comment`, `pull_request_review_comment`, `pull_request_review`, and `issues` events — invokes `claude-code-action` when a human mentions `@claude` (all bot actors excluded via `sender.type != 'Bot'`)

### Known Limitation: `pull_request_review` trigger and OAuth

`claude-code-action` with `claude_code_oauth_token` (OIDC) requires the triggering actor to have write access to the repo. Bot-triggered `pull_request_review` events (e.g. from `copilot-pull-request-reviewer[bot]`) fail with 401 because the bot actor lacks write access. This means a separate triage workflow triggered by `pull_request_review` is **not viable** with OAuth auth. Bot reviewer triage must stay within the main review prompt (triggered by `pull_request` where the actor is the PR author).

### Known Limitation: a PR editing a caller workflow gets no Claude review

`claude-code-action` requires the **triggering caller** workflow file to be identical to its version on the default branch. Where it differs, the OIDC token exchange returns a workflow-validation error, the action logs `Workflow validation failed`, throws `WorkflowValidationSkipError` — which its retry wrapper explicitly excludes from retry — and the step still exits 0. The job is green, no review is posted, and nothing on the pull request surface says so.

The guard covers the caller only, not the reusable workflow it calls: PR #88 changed `reusable-claude-code-review.yml` alone and received a full review, while PR #91 also changed `claude-code-review.yml` and received none (measured 2026-08-19 on run `32273783450`).

So a change to a caller workflow cannot be reviewed by Claude on its own branch and only takes effect once merged. Never read a green `claude-review` check on such a pull request as a clean review.

## Pre-commit

This repo uses pre-commit hooks including `zizmor` (GitHub Actions security linter) and `actionlint` (workflow syntax checker). Commits that fail these checks should not be pushed.
